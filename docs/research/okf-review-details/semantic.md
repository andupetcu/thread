## Main distinction

This subsystem authors and deploys a business semantic model. It is not the portable OKF bundle implementation and should not become a prerequisite for Thread bundle authoring. Its normative wire format is Apache Ossie `0.2.0.dev0` or the Google extended `0.2.0.dev0/google` profile (`toolbox/mdcode/docs/semantic-model/model_spec.md:18`). Both load into an IR of entities, attributes, directed relationships, metrics, optional actions and constraints (`toolbox/mdcode/src/libts/semantic/ir.ts:43`). The subsystem can publish metadata to Knowledge Catalog, compile a property graph over existing BigQuery or Spanner tables, or import a limited Turtle ontology. Those are separate consumers/integrations from packaging notes and context in an OKF directory.

The loader requires a declared version, gates native extensions vs opaque vendor carrier by that version, accepts YAML/JSON, normalizes alias/shorthand syntax, and attaches source-document names to diagnostics (`loader.ts:609`, `loader.ts:648`, `loader.ts:1171`; paths in this report without prefixes are relative to `toolbox/mdcode/src/libts/semantic/`). The extended profile adds entities alias, inheritance, abstract classes, deployment target, actions and constraints; it rejects `custom_extensions`. Serializer output always chooses the Google extended version, not vanilla Ossie (`osi_converter.ts:52`, `osi_converter.ts:161`). Do not label this syntax itself as OKF or infer OKF versioning rules from it.

## Reusable architecture and maintenance patterns

1. **Pure content pipeline before effects.** Parsing/normalization, structural validation, target-specific generation, and side-effectful publishing are separate. `knowledge_catalog.ts:112` produces entries, links, warnings and owned prefixes without network access; `deploy_knowledge_catalog.ts:161` writes an already-emitted plan independent of its origin. `converters/owl/convert.ts:40` composes parser, policy mapper and serializer. For Thread, use an independently testable note-to-bundle model and writer, then separate export-to-directory/archive or optional provider adapters. A cloud account should not be needed to validate a portable bundle.

2. **Keep authoring source separate from projections.** `resolve_inheritance.ts:48`, `resolve_profiles.ts:63`, and `transpile.ts:105` clone inputs rather than mutate them. `resolve_profiles.ts:277` explicitly reports unavailable fields/entities/metrics/relationships. This is a useful pattern for selected-note exports: retain canonical notes, source IDs/revisions, and export configuration; derive the selected bundle from them; show omitted/dangling content with reasons. Do not silently rewrite canonical notes to match a reduced export.

3. **Explicit ownership and conservative reconciliation.** The emitter returns `ownedPrefixes`, so the writer does not guess which resources belong to a model (`knowledge_catalog.ts:88`). Reconciliation only deletes owned resources absent from the new set; empty ownership prefixes are filtered; replacement links are written before old links are removed (`deploy_knowledge_catalog.ts:301`, `deploy_knowledge_catalog.ts:345`, `deploy_knowledge_catalog.ts:479`). Foreign model replacement is explicitly gated (`deploy_knowledge_catalog.ts:271`). For repeated bundle exports, persist owned output paths and stable source-to-output identities. Clean up only generated files, and detect user edits or name collisions rather than overwriting unrelated content.

4. **Complete reads and deterministic results.** `pull_kc.ts:54` refuses multiple anchors and aborts on failed entry/aspect/link hydration instead of writing an incomplete model. Its concurrency pool caps at eight and preserves input ordering (`pull_kc.ts:177`). A Thread import/refresh should complete discovery/validation before committing state, preserve deterministic ordering, and report true success counts.

5. **Provenance and loss are product concepts.** `docs/semantic-model/fidelity.md:1` explicitly distinguishes authored content, catalog metadata and queryable projection. The OWL converter reports counts of actually converted constructs, not source counts (`converters/owl/to_ir.ts:48`). This is directly relevant to bundle maintenance: retain original content and metadata, preserve unsupported material when possible, and expose concrete losses when an export target cannot represent something.

6. **Absent capability is not an empty value.** Binding profiles distinguish an unavailable field from a bound field whose value is null (`docs/semantic-model/profiles.md:128`). For bundle selection, a missing note, excluded attachment or unresolved link should be distinguishable from intentionally empty text.

## What is unnecessary for portable OKF bundles

Do not require BigQuery, Spanner, gcloud credentials, IAM permissions, Dataplex entry groups/types/aspects, SQL expression transpilation, physical table bindings, profile merging, graph DDL, model metrics, class inheritance, OWL reasoning, or action execution merely to create or maintain a portable OKF bundle. All arise from this subsystem's optional semantic-model/deployment goals.

The BigQuery generator compiles nodes/edges and selected single-aggregate measures over existing tables (`bigquery.ts:60`). The Spanner generator has a different output capability: no measures or metadata OPTIONS, bare table names (`spanner.ts:1`). `deployment_target.ts:28` recognizes only their two Google resource-URI shapes. These are adapter details rather than portable bundle constraints. If Thread later supports structured semantic-model content, it can retain the authored YAML as content first and add specialized authoring or publishing separately.

Likewise, actions are declarative descriptions of MCP/REST/gRPC executors and typed parameters. They are published to Knowledge Catalog only; kcmd never calls their executors. Constraints and guards have no runtime evaluation or enforcement (`ir.ts:389`, `docs/semantic-model/actions.md:144`). Importing an action declaration must not be treated as permission to execute it, and a UI must not imply that a declared guard makes an action safe or enforced.

## Important fidelity limits

- Default Knowledge Catalog publication does not store field/metric SQL expressions. `--emit-expressions` is off because live system templates do not yet support the fields (`knowledge_catalog.ts:75`, `knowledge_catalog.ts:443`, `knowledge_catalog.ts:485`). Pull can therefore serialize metrics without required expressions. Keep source documents; KC pull is not a backup/restore format for them.
- Catalog output drops entity inheritance and abstract entities; skips logical relationships without join columns and M:N association edges (`knowledge_catalog.ts:151`, `knowledge_catalog.ts:267`). It does not preserve ordinary model/entity/metric synonyms and examples, field-level AI context, or vendor expression variants. Constraint custom aspects preserve their full AI context, while action aspects preserve only instructions (`kc_constraints.ts:133`, `kc_actions.ts:154`).
- IDs derived by slugging may collide, and relationship IDs are lowercased, normalized and capped at 63 characters (`knowledge_catalog.ts:677`, `knowledge_catalog.ts:701`). A source name is not a reliable immutable identity. Thread should use stable note IDs and an explicit mapping, with display names separate.
- Serializer round trips normalize comments/key ordering and collapse dialects to at most canonical plus one imported form. It drops extensions unsupported by `/google` (`osi_converter.ts:22`, `osi_converter.ts:402`). A general portable bundle writer should preserve opaque assets rather than route everything through this lossy codec.
- OWL import is intentionally one-way and lossy. It maps classes to entities, datatype properties to fields, object properties to directed edges and named subclass relations to inheritance. It drops term IRIs, most OWL axioms/annotations, richer class expressions, individuals, and non-Turtle serializations (`converters/owl/to_ir.ts:21`, `docs/semantic-model/owl-import.md:407`). Local-name collisions keep the first and warn (`converters/owl/to_ir.ts:221`). Preserve the original Turtle asset if supporting ontology content.

## Caveats found by comparing implementation to prose

These are static observations, not executed bug reproductions, and primarily caution against copying code/contracts indiscriminately:

- Documentation says a rejected model never half-deploys (`docs/semantic-model/reference.md:48`), but sequential graph writes are expressly not rolled back (`deploy_bigquery.ts:253`, `deploy_spanner.ts:183`), and catalog phases can fail after earlier writes. Treat validation-before-write as helpful preflight, not a transaction guarantee. For local bundle export, staging plus atomic replacement is preferable where feasible.
- The loader claims every object is closed, but shared nested expression/AI-context/dimension/custom-extension schemas use ordinary `z.object` without `.strict()` (`loader.ts:63`–`loader.ts:104`). Higher-level objects are strict. Unknown nested fields may be stripped. Thread should define preservation/rejection rules at every level of its actual OKF schema.
- `osi_converter.ts:249` warns that fields require expressions and cannot reload without them, but the current loader accepts expression-less fields (`loader.ts:306`). This warning is stale; metric expressions remain required. Several OWL staging comments still claim opaque carriage that the mapper removed. Follow code plus normative scope, not isolated comments.
- `resolve_profiles.ts:207` calls its predicate a bare-column check but only rejects whitespace/parentheses; text such as `a+b` passes. Its cross-entity availability check merely tests whether any surviving relationship connects any two referenced entities, not whether the full dependency graph is connected (`resolve_profiles.ts:427`). These are not sufficiently general validators to transplant into a bundle system.
- `deploy_knowledge_catalog.ts:650` treats 403/404 link-aspect update failures after create-conflict as successful no-ops, so re-push can leave stale aspects. Concurrent write phases also can underreport successful writes when another write in the same wave fails (`deploy_knowledge_catalog.ts:613`). Bundle maintenance should report partial changes honestly and verify convergence.

## Proposed Thread boundary

Implement portable bundle creation/maintenance around canonical notes, stable note identities, explicit selection/dependency policy, metadata authoring, deterministic materialization, validation, export diff and source-change tracking. Keep semantic-model editing and Google publication as optional later integrations. Preserve authored/source assets and distinguish source truth from generated projection. The parent's direct OKF spec review must define actual required files and metadata; this semantic scope supplies useful architecture, not that format's normative requirements.
