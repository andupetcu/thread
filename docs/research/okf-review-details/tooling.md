## Recommendation for Thread

Implement a small portable OKF document/bundle domain and import/export service in Thread. Reuse format concepts and examples, not `kcmd` as Thread's persistence engine. Keep original Markdown/body and unrestricted producer extensions round-trippable alongside typed projections for editing/search. Cloud publishing is a later optional adapter with a reviewed change plan. Neither the Google metadata-as-code format (`catalog.yaml` + catalog tree, Google aspects) nor OSI/Ossie semantic-model YAML is the portable OKF bundle format.

## Main findings

1. **General metadata-as-code sync is materially less complete than advertised.** README promises pending-change conflict detection, minimal pushes, dry runs, status, and MCP pull/push (`toolbox/mdcode/README.md:158-171`, `229-239`). Actual generic `CatalogSync` has TODOs for conflicts/local deletes/checksums (`src/libts/sync.ts:40-42`, `78-80`), `validate()` and `status()` throw (`134-139`), push always iterates entries and writes selected aspects, and `force` is unused. CLI has no status command. `commands.pull()` accepts dryRun but invokes `sync.pull()` without it for non-semantic scopes (`src/tool/commands.ts:272-284`), so `kcmd pull --dry-run` on a KB can overwrite local documents. `--validate-only` push suppresses writes but is not complete schema validation. Missing/inaccessible pull entries are skipped while success is returned (`sync.ts:50-56`). Do not use this as conflict-safe user-note sync.

2. **Even local read/edit depends on Google access.** `CatalogSnapshot.fromPath()` loads manifest/source and fetches type definitions (`src/libts/snapshot.ts:33-44`, `142-180`); KB and entry-group source construction calls live `getEntryGroup` (`src/libts/source.ts:36-48`, `75-86`). `ApiContext.default()` shells to gcloud three times for project/region/token (`src/libts/gcp/context.ts:31-41`). MCP initialization does the same (`src/tool/mcp.ts:17-18`). The enrichment agent invokes it at module initialization (`toolbox/enrichment/src/agent/enrich/agent.ts:87`). Plain import of the mdcode library does not itself call gcloud, but its advertised normal snapshot workflow does. Node-compatible pure document handling should be separate from credentials/cloud clients.

3. **OKF support is a demo adapter, not a core typed OKF API.** `demo/okf/okf.ts:1-7` explicitly isolates all OKF knowledge in the demo. Generic DocumentsLayout maps title/description/tags/timeStamp/body plus `catalogEntry` passthrough, interpreting `type` as a three-part Google type (`src/libts/layouts/documents.ts:185-219`). Passing raw OKF directly drops `resource`, sources, generation, verification, lifecycle and computation contracts. The demo stages those in a project/location-specific `okf` aspect and `okf-bundle` entry type (`demo/okf/okf.ts:214-278`); the 331-line custom aspect JSON models the v0.2 signal contract plus JSON extras. Keep these Google-specific transport details out of Thread's authoring model.

4. **Bridge round-trip is limited, despite broad lossless wording.** It copies only `.md` files (`demo/okf/okf.ts:130-140`, push.ts:30-34); non-Markdown attachments such as attester Python, computation SQL files, and generated viewer files are not transported. Body links remain Markdown, not native catalog edges; only hierarchy is derived (`demo/README.md:240-244`). Serializer trims the body and normalizes YAML (`demo/okf/okf.ts:186-188`), singleton verified mappings become lists (`253-255`), empty tag arrays disappear via generic layout (`documents.ts:239`), `pick` and nested `divert` discard null values (`okf.ts:204-208`, `229-234`), including null producer subfields. Thus extension value fidelity and byte fidelity are not universal. Build exact import/export and attachment tests rather than adopting the claim as guarantee.

5. **Untrusted `extra` paths can modify prototypes.** `demo/okf/okf.ts:191-200` traverses ordinary objects without own-property checks and assigns arbitrary path segments. `fromStaging` restores unvalidated JSON `[path,value]` pairs at `314-316`. A `__proto__` segment can traverse into Object.prototype; `constructor/prototype` is another dangerous path. Reject prototype keys and validate path shape/index bounds or use safe maps/own-property-only reconstruction. This is a static finding; no exploit executed.

6. **Filesystem helpers are not safe bundle import boundaries.** DocumentsLayout saves `name + .md` through `path.join` without containment checks (`src/libts/layouts/documents.ts:98-117`); StandardLayout does likewise (`standard.ts:74-79`). Names derived from remote Entry IDs can contain directory components (`sources/kb.ts:36-43`, `sources/entrygroup.ts:38-45`). `demo/okf/listMarkdown` follows symlink directories (`okf.ts:134`). Python fileskb containment uses string startswith rather than component-aware ancestry (`samples/enrichment/src/tools/fileskb/main.py:17-24`), allowing sibling prefixes; TypeScript fileset improves lexical prefix checking but never realpaths, so a symlink can escape (`toolbox/enrichment/src/tools/md/fileset.ts:23-30`, `51-56`). Both expose arbitrary regex search without bounds. Thread needs normalized relative POSIX paths, root containment, symlink policy, collision detection, file/count/size limits, and staged atomic imports.

7. **Enrichment skills can execute arbitrary local code.** Python explicitly constructs `UnsafeLocalCodeExecutor` (`samples/enrichment/src/enrichment/documentation/sources.py:57-71`); TypeScript repeats it (`toolbox/enrichment/src/agent/tools.ts:69-85`). Both load executable MCP command/args/env or remote URLs from configuration (`sources.py:18-54`, `tools.ts:16-61`). That is trusted operator configuration, not ordinary bundle data. Treat imported SKILL.md, attesters, executor descriptions, SQL fences, and configuration as inert authoring content by default. These enrichment packages also call Vertex/Gemini and can send note/metadata/tool result content to the model. They are optional later integrations, not necessary for hand authoring.

8. **Demo cleanup does not actually bind project/location to its manifest.** `manifestEntryGroup()` returns only the last scope component (`demo/okf/okf.ts:86-93`), while cleanup gets project/location from current gcloud context (`cleanup.ts:5-7`, `17-28`). Changing ambient gcloud project/region after setup can delete the same-named group elsewhere. Setup also adopts an existing group (`setup.ts:50-55`), so the comment that cleanup only undoes resources it created is stronger than its guarantee. Push/pull similarly compute aspect keys from ambient context while copying the stored scope. Do not reuse these scripts for app-managed publishing. Older BQ/KB demo setup/cleanup scripts are top-level executable cloud mutations (BQ cleanup DROP SCHEMA CASCADE; KB cleanup quiet delete).

9. **Docs contain future design and stale API examples.** Alias and EntryLink support is described extensively (`docs/concept.md`, `docs/spec.md`) but generic manifest schema has only scope/default_profile/snapshot/publishing entries/aspects (`src/libts/manifest.ts:11-24`), rejects one-part references (`125-175`), and no generic alias machinery. StandardLayout has no Markdown sidecar implementation despite diagrams. README says Python library but it remains future plan (`docs/plan.md:41-47`). MCP actually exposes only list-entries, lookup-entry, modify-entry (`src/tool/mcp.ts:20-92`), with resource updates limited to description (`snapshot.ts:76-85`). Review source behavior, not aspirational docs, when writing the plan.

10. **OSI/semantic-model commands are a distinct deployment pipeline.** Semantic layout stores model YAML under `catalog/EntryGroups/<group>`, has profile files, and deliberately returns no entry list (`src/libts/layouts/semantic-model.ts:65-91`). CLI imports OWL to OSI and dispatches semantic graph deploys to BigQuery/Spanner and catalog. This is not conversion of OKF prose/link graphs to executable semantic models. Its push loop validates/deploys profile by profile and deploys graph legs before catalog (`src/tool/commands.ts:569-617`, `663-673`), so later failure can leave earlier external writes. Do not conflate these graphs or offer them as native Thread bundle export targets in the initial plan.

## Other observations

- Metadata/document forms are broad `any` maps, not reusable strict OKF validators (`src/libts/metadata.ts`). `parseMarkdown` assumes parsed YAML mapping (`documents.ts:196-200`) and errors on empty/null frontmatter; malformed delimiters become body. Thread should validate malformed input explicitly and retain it for repair rather than silently reinterpret.
- TypeScript enrichment monkey-patches ADK global prototypes and closes all globally tracked MCP sessions when any runner finishes (`toolbox/enrichment/src/agent/utils/patchadk.ts:31-40`, `66-103`). This is unsuitable to embed unchanged in a concurrent long-running Node app. protobuf patch likewise mutates globals for Bun bundling.
- Root README explicitly says not an official Google product (`README.md:25`). Root LICENSE is Apache 2.0; both TypeScript package.json files say ISC (`toolbox/mdcode/package.json:26`, `toolbox/enrichment/package.json:21`). Record this metadata discrepancy if vendoring; prefer implementing the portable standard independently.
- GA4 demo bundle provides practical links/index/navigation fixtures, not verified analytical truth. Its dataset says end date Jan 1 (`demo/okf/catalog/datasets/ga4_obfuscated_sample_ecommerce.md:25`), while table prose says Jan 31 (`tables/events_.md:27`); high-active-user threshold multiplies millisecond measure by 1,000,000 (`references/metrics/highly_active_users.md:56`); frequent users counts event_date without DISTINCT in HAVING (`frequently_active_users.md:55`). Imported generated examples should preserve provenance, not gain verified status automatically.
- Python discovery is a cloud semantic-search agent, not a local bundle index; it reads only response.results at the first response and returns resource descriptors. Useful pattern: query decomposition + result deduplication, not required infrastructure.

## Suggested plan acceptance criteria

Local creation/editing works offline without gcloud, model provider, Bun CLI, or Google account. Import previews all files, safe paths, metadata diagnostics, broken/ambiguous links and missing attachments before commit. Portable export includes authored Markdown, all supported non-Markdown attachments, frontmatter-free indexes, and preserved unknown metadata. Draft/verification/provenance are user-visible and never inferred from successful import or pretty rendering. Export/import tests compare parsed metadata, exact retained extension values, body/attachments and link targets; separate optional normalization from default preservation. Google publishing, OSI deployment, enrichment agents, execution and attestation runners remain explicit later capabilities with independent trust and change-review boundaries.
